# GraphRAG Q&A

1. 向量 RAG 是把文档切片后按相似度捞回片段，本质上看到的永远只是局部。GraphRAG 通过实体、关系、社区报告把整篇语料"压成结构"再回答，这种差别在哪类问题上才真正体现出价值？是不是只有"整体性、归纳性、对比性"的问题（比如"这些公司有什么共同点"）才值得上 GraphRAG？普通事实查询用它反而是杀鸡用牛刀？
2. GraphRAG 索引阶段要对每个文本块跑实体抽取、关系抽取、社区报告生成，几万段文本就是几万次 LLM 调用，一次完整索引动辄几小时、几十美元。这种代价到底什么样的项目才值得？有没有办法在不损失太多质量的前提下，把贵的环节（比如社区报告）做成增量或按需触发？
3. 实体抽取完全依赖 LLM，而 LLM 抽错了实体或者关系会被沉淀进图里，下游 local/global search 都基于这张图。这种"上游错误下游放大"的风险该怎么评估？有没有什么手段在索引阶段就能检测出明显错误的三元组，而不是等到查询时才发现答非所问？
4. 同一个人物在不同段落里可能叫"马云"、"马总"、"阿里巴巴创始人"，GraphRAG 怎么把它们合并成同一个节点？合并粒度太粗会把不同人误并，太细又会把同一个人拆成多个孤立节点——这两种错误哪种对查询效果伤害更大？工程上有没有可调的阈值或者人工校验环节？
5. 社区检测（Leiden 算法）本质上带有随机性，同一份数据跑两次可能生成略有差异的社区划分，进而生成不一样的社区报告。这种不确定性对 global search 的答案稳定性影响有多大？要不要在生产里固定随机种子？社区粒度（层级）应该怎么选才算合理？
6. Local、Global、DRIFT 三种查询方式各有适用场景，但实际用户提问时并不会主动告诉你"这是个全局问题"。怎么自动判断一个问题该走哪条路？让 LLM 先做一次问题分类靠不靠谱？要是分错了，回退策略应该怎么设计？
7. Global Search 实际上读的是 LLM 生成的"社区报告"，而社区报告又是从原文压缩出来的——这等于让模型读自己写的二手摘要去回答问题。这种"概要的概要"会不会在多跳推理时越走越偏？怎么验证全局答案没有偏离原文事实？
8. 文档增删改时整张图怎么更新？新加一篇文档可能影响已有的实体合并、社区划分和社区报告，最坏情况是不是要全量重建？有没有像向量库那样的"增量索引"方案，或者业界一般用什么折中做法（比如定期重建 + 中间增量打补丁）？
