# RAG Q&A 汇总

> 汇总 stage2-advanced/03-rag 各子专题（Naive RAG / Advanced RAG / GraphRAG）的开放性问题。

---

## 一、Naive RAG

1. langchain_community.document_loaders 的 lazy_load() 方法底层原理是什么（哪些场景下使用更有收益）？如何进行重载？
2. 对于一些复杂 PDF，比如有图层 pypdf 无法识别文档内容的情况下最佳实践是什么？OCR 吗？如果不是我们怎么做？
3. 既然 Embedding Model 在 RAG 流程中很重要，那么我们在选择 Embedding Model 时应该考虑哪些因素？怎么评判 Embedding 模型向量化的质量？
4. chunk size 和 chunk overlap 的取值如何影响 Embedding 和下游的检索效果？有没有实际的例子说明它们之间的直接关系？
5. 为什么调试 RAG runnable pipeline 比较麻烦？为什么要使用 astream_events 来调试？有没有其他更好的调试方法？
6. LLM Eval 的框架比如现在的 Terminal-bench 和常见的 LLM as Judge 方法和 Ragas 在设计和底层原理上有没有根本的不同？Ragas 说到底也是 LLM as Judge 的一种吧？如何规避模型当裁判的时候裁判本身存在幻觉或者不确定性的问题？还有就是 LLM 界的通病：Ragas 离线分数高 ≠ 用户满意。线上真实用户满意度跟离线评分的相关性到底有多强？怎么验证？
7. 向量化是离线昂贵、检索是在线轻量的。当 PDF 库的文档增 / 删 / 改时，向量库怎么增量更新？什么时候必须全量重建？
8. 如果是多用户 SaaS 场景：用户 A 上传的私密文档怎么保证不被用户 B 查到？租户隔离应该做在向量库层还是检索层？这个有没有什么最佳实践？
9. 怎么让系统知道"这个问题在我的知识库里没有"？光靠 prompt 让 LLM 说"不知道"够吗？有没有更可靠的机制？
10. 考虑成本的话，embedding API 调用 = 索引时的 chunk 数 + 每次查询？怎么算清楚一个 RAG 项目的 token 预算？哪一块最容易花超？

## 二、Advanced RAG

1. 对于语义分块有的块大、有的块小的问题，有没有可能在特殊场景下导致语义检索的不稳定？正如大块和小块的那种矛盾，语义分块有没有可能分出来检索效果还不如 Naive RAG 的块？这种情况下我们是考虑句子窗口分块还是退回到 Naive RAG？
2. 混合检索除了加权平均之外是不是还有别的策略？级联检索和交叉验证这些在哪些场景下适用？有没有一些实际的例子可以说明这些策略的优缺点和适用场景？
3. RRF 实际上可不可以理解为就是一种简单的加权平均？它和其他加权平均方法相比有什么独特的优势或者局限性？在实际应用中我们应该如何选择使用 RRF 还是其他加权平均方法？
4. Cross-Encoder（比如 bge-reranker-v2-m3）和向量检索的根本差别在于：前者把 query 和 doc 拼在一起进同一次 attention，后者各自独立向量化。这种"晚交互"为什么效果更好？既然 Cross-Encoder 这么强，为什么不能直接用它检索全库、跳过向量检索这一步？两者结合的本质是不是就是召回靠快、排序靠准的算力权衡？
5. 让 LLM 直接给 (问题, 文档) 打 0-10 分这种做法，结果到底稳不稳？同一个文档调用两次可能分数都不一样，不同文档之间的分数也不一定可比（毕竟 LLM 没看到其他候选）。要不要改成一次喂多个文档让它直接排序？这两种打分方式在准确率和成本上各有什么取舍？
6. Long Context Reorder 的"奇数前、偶数倒序"是基于 Lost in the Middle 的经验法则，但这个现象在不同 LLM 上的强度并不一致（GPT-4、Claude、Qwen 都有差异）。这种重排是不是应该针对具体模型做实验验证？如果模型本身已经做了长上下文优化，强行 reorder 会不会反而引入噪声？
7. 上下文压缩让 LLM 从每个文档里抽相关句子，本质上是用一次额外的 LLM 调用换 token 节省，但同时也把"抽错"这个新风险引入了进来。在什么场景下压缩带来的收益（省 token、减少干扰）大于风险（漏掉关键信息、抽取幻觉）？有没有什么办法能评估压缩到底丢了多少东西？
8. Self-RAG 设计了四个反思点，每个都是一次 LLM 调用，最坏情况下回答一个问题要调用五六次模型。这种延迟和成本在生产环境真的扛得住吗？反思链条上某一步判断错了会不会一路错下去？能不能像原论文那样把反思能力蒸馏到一个小模型里？
9. Adaptive-RAG 的 A/B/C 三档分类完全依赖 LLM 自己判断问题复杂度，但 LLM 很容易把"看着简单的难题"误判成 A 类直接答，或者把"看着复杂的简单题"误判成 C 类去多步检索。这个分类器自己的准确率怎么评估？要不要干脆换成一个微调过的小模型来做路由？
10. 带引用的生成靠 LLM 自己在回答里标注 `[文档X]`，但模型经常乱标、漏标，甚至引用了根本没用到的文档。这种"引用幻觉"该怎么评估和缓解？除了在 prompt 里约束之外，有没有结构化输出或者事后用归因模型校验的做法？像 Perplexity 这类产品的引用机制大致是怎么做的？

## 三、GraphRAG

1. 向量 RAG 是把文档切片后按相似度捞回片段，本质上看到的永远只是局部。GraphRAG 通过实体、关系、社区报告把整篇语料"压成结构"再回答，这种差别在哪类问题上才真正体现出价值？是不是只有"整体性、归纳性、对比性"的问题（比如"这些公司有什么共同点"）才值得上 GraphRAG？普通事实查询用它反而是杀鸡用牛刀？
2. GraphRAG 索引阶段要对每个文本块跑实体抽取、关系抽取、社区报告生成，几万段文本就是几万次 LLM 调用，一次完整索引动辄几小时、几十美元。这种代价到底什么样的项目才值得？有没有办法在不损失太多质量的前提下，把贵的环节（比如社区报告）做成增量或按需触发？
3. 实体抽取完全依赖 LLM，而 LLM 抽错了实体或者关系会被沉淀进图里，下游 local/global search 都基于这张图。这种"上游错误下游放大"的风险该怎么评估？有没有什么手段在索引阶段就能检测出明显错误的三元组，而不是等到查询时才发现答非所问？
4. 同一个人物在不同段落里可能叫"马云"、"马总"、"阿里巴巴创始人"，GraphRAG 怎么把它们合并成同一个节点？合并粒度太粗会把不同人误并，太细又会把同一个人拆成多个孤立节点——这两种错误哪种对查询效果伤害更大？工程上有没有可调的阈值或者人工校验环节？
5. 社区检测（Leiden 算法）本质上带有随机性，同一份数据跑两次可能生成略有差异的社区划分，进而生成不一样的社区报告。这种不确定性对 global search 的答案稳定性影响有多大？要不要在生产里固定随机种子？社区粒度（层级）应该怎么选才算合理？
6. Local、Global、DRIFT 三种查询方式各有适用场景，但实际用户提问时并不会主动告诉你"这是个全局问题"。怎么自动判断一个问题该走哪条路？让 LLM 先做一次问题分类靠不靠谱？要是分错了，回退策略应该怎么设计？
7. Global Search 实际上读的是 LLM 生成的"社区报告"，而社区报告又是从原文压缩出来的——这等于让模型读自己写的二手摘要去回答问题。这种"概要的概要"会不会在多跳推理时越走越偏？怎么验证全局答案没有偏离原文事实？
8. 文档增删改时整张图怎么更新？新加一篇文档可能影响已有的实体合并、社区划分和社区报告，最坏情况是不是要全量重建？有没有像向量库那样的"增量索引"方案，或者业界一般用什么折中做法（比如定期重建 + 中间增量打补丁）？
