## 一、Naive RAG

1. 4 代 RAG 范式演进：naive rag → advanced rag → graph rag → agentic rag
2. RAG 的基本流程：

```
文档 → Chunk → Embedding → Vector Store → (Query Embedding) → Retrieve → Prompt → Model → Answer
```

需要注意的是 Embedding Model 在这个过程中很重要，文本片段向量化以及用户提问转查询向量化都依赖于 Embedding Model 的质量。

### 1.1 文件加载注意事项

1. 编码：确保文件编码正确，常见的编码格式有 UTF-8、GBK 等。错误的编码可能导致文本内容无法正确读取。
2. 大文件处理：大文件一次性加载内存可能溢出，懒加载、分批处理以及流式处理是常见的解决方案。
3. PDF 中出现复杂结构：PDF 文件可能包含表格、图像等复杂结构，使用专门的 PDF 解析库（如 PyPDF、pdfplumber、langchain 的 unstructured loader）可以更好地提取文本内容。
4. 网页动态内容：如果需要从网页加载数据，可能会遇到动态内容加载的问题，使用 Selenium、Playwright 等工具可以模拟浏览器行为，获取完整的网页内容跳过 js 渲染的内容无法获取的问题。

### 1.2 文本分割

三个问题：

1. 语义稀释，长文档直接 embedding 会导致语义稀释，无法捕捉到文档的细节信息。
2. 检索噪声，过大的文本块可能包含不相关的信息，增加检索的噪声。
3. 上下文限制，模型的输入长度有限，过长的文本块可能超出模型的输入限制，导致无法处理。

在使用 splitter 的过程中，chunk size 和 chunk overlap 是两个重要的参数：

- chunk size：每个文本块的最大长度，通常根据模型的输入限制和文本内容的特点来设置。具体要看下游的 Embedding Model 或者其他模型的输入限制来设置，通常建议设置在模型输入限制的 70%-80% 左右，以留出足够的空间给其他输入内容。
- chunk overlap：文本块之间的重叠部分，通常设置为 chunk size 的 10%-20% 左右。重叠部分可以帮助模型更好地理解文本块之间的关系，减少信息丢失。

合适的 separator 可以帮助 splitter 更好地分割文本，常见的 separator 有换行符、句号、空格等。选择合适的 separator 可以根据文本内容的结构来决定，例如对于段落较长的文本，可以使用换行符作为 separator，而对于句子较短的文本，可以使用句号作为 separator。

### 1.3 Embedding Model 嵌入模型与嵌入的方式

简单理解：嵌入是把文本转为高维向量的过程，嵌入模型是执行这个过程的工具，我们说的语义相似其实就是向量空间中的距离，高维向量在向量空间中越接近的文本在语义上也更相似。

主流的 Embedding 模型选择：

| 模型                    | 提供商      | 维度 | 特点               | 适用场景     |
| ----------------------- | ----------- | ---- | ------------------ | ------------ |
| text-embedding-3-small  | OpenAI      | 1536 | 性价比高，效果好   | 通用场景     |
| text-embedding-3-large  | OpenAI      | 3072 | 最高精度           | 高精度需求   |
| bge-large-zh            | HuggingFace | 1024 | 中文优化           | 中文场景     |
| bge-m3                  | HuggingFace | 1024 | 多语言支持         | 多语言场景   |

### 1.4 向量数据库

向量数据库主要 4 件事：

1. 存储向量：将文本块的向量表示存储在数据库中，通常使用高效的数据结构来支持快速查询。
2. 索引构建：构建索引以加速向量检索，常见的索引方法包括树结构、哈希表等（HNSW、IVF、PQ 和 FLAT 为主）。
3. 向量检索：根据用户查询的向量表示，检索与之相似的文本块，通常使用距离度量（如欧氏距离、余弦相似度、点积）来衡量向量之间的相似度，最后返回 Top K 个最相似的文本块。
4. 更新和维护：支持向量的更新和维护，包括添加新的向量、删除旧的向量以及重新构建索引等操作。

主流向量数据库的对比：

| 数据库     | 类型         | 特点                  | 推荐场景                    |
| ---------- | ------------ | --------------------- | --------------------------- |
| Chroma     | 本地/嵌入式  | 简单易用，教学首选    | 开发调试、小规模应用        |
| FAISS      | 本地库       | Meta 开发，速度极快   | 大规模高性能场景            |
| Pinecone   | 云服务       | 全托管，开箱即用      | 生产环境                    |
| Milvus     | 分布式       | 开源，支持海量数据    | 企业级大规模部署            |
| Weaviate   | 云/自托管    | 支持混合搜索          | 需要关键词+向量混合检索     |

从上手的容易程度来说，Chroma 是最简单的，Pinecone 需要一定的环境配置，FAISS 则完全免维护，Milvus 和 Weaviate 适合有分布式需求的企业用户。该项目我们使用 Chroma 作为示例，后续可以根据需要切换到其他数据库。（参考 `stage2-advanced/03-rag/01_naive_rag/04_vector_store/01_chroma_from_texts.py` 等。）

#### Chroma 四种构建索引方式的对比

| 构造方式                       | 一句话说明                  | 是否支持 metadata | 是否适合 RAG | 典型用途              |
| ------------------------------ | --------------------------- | ----------------- | ------------ | --------------------- |
| `from_texts()`                 | 直接从 string 构建向量库    | ×                 | 不推荐       | Demo、小测试          |
| `from_documents()`             | 从 Document 列表构建向量库  | ★★★★★             | 必需         | 实际项目、RAG         |
| `Chroma(persist_directory=…)`  | 加载已有向量库              | ★★★★              | 必需         | 持久化、生产环境      |
| `Chroma(client=…)`             | 使用 server 模式            | ★★★★              | 可选         | 大规模服务端部署      |

### 1.5 Retriever 检索器（或者叫召回器）

简单来说检索器将用户查询转为向量表示，并在向量数据库、BM25 索引或者其他的数据源中检索与之相似的文本块。

#### 检索器常见参数说明

| 参数 | 适用检索类型 | 作用说明 |
| --- | --- | --- |
| `k` | similarity / mmr | 返回 Top-k 个最相似文档（最常用） |
| `fetch_k` | mmr | 先从向量库取更多文档，再过滤成 k 个（提高结果多样性） |
| `lambda_mult` | mmr | 控制"相关性 vs 多样性"权重（MMR 专用，取值 0-1） |
| `filter` | similarity / mmr | 根据 metadata 过滤文档（例如筛选某个文件来源） |
| `score_threshold` | similarity | 设置相似度最低阈值（低于就不返回） |
| `distance_metric` | 部分向量库 | 指定向量距离算法（cosine / L2 / dot 等） |

#### k 值的选择经验

| 场景 | k 推荐 |
| --- | --- |
| 结构清晰的内容（FAQ、定义类问答） | 2-4 |
| 数据较碎、chunk 很小，让 LLM 自行总结 | 5-8 |
| 需要广泛上下文 / 复杂查询多角度交叉引用 | 8-12 |

#### MMR 参数调优指南

| 参数 | 建议值 | 调优策略 |
| --- | --- | --- |
| `k` | 2-4 | 根据上下文窗口大小和 chunk 长度调整 |
| `lambda_mult` | 0.5-0.7 | 偏向相关性用 0.7+，偏向多样性用 0.3-0.5 |
| `score_threshold` | 0.6-0.8 | 宁缺毋滥用高阈值，召回优先用低阈值 |
| `fetch_k` | k 的 3-5 倍 | MMR 候选池大小，太小退化成 similarity，太大引入噪声 |

### 1.6 RAG Runnable Pipeline

#### 核心价值

LangChain 的 RAG 抽象不是"让 RAG 变聪明"，而是给一个充满胶水代码的领域提供 **"标准库 + 词汇表 + 生态系统"**。可以类比 Flask 之于 Web、pandas 之于数据。

它解决的四件事：

1. **词汇标准化** — `DocumentLoader / TextSplitter / Embeddings / VectorStore / Retriever / OutputParser / Tool` 全行业共识，协作、招聘、开源代码迁移成本骤降。
2. **集成生态** — 200+ Loader、几十个向量库、所有主流 LLM Provider 都有官方 wrapper。这是它真正的护城河。
3. **LCEL 组合范式** — `prompt | model | parser` 这个串联自带 stream / batch / async / astream_events，自己手写支持完整这四件套代码量会爆炸。
4. **端到端栈** — LangServe（部署）+ LangSmith（可观测性 / 评测）+ LangGraph（复杂工作流）原生集成，从 prototype 到 production 的路径相对完整。

它**不**解决的事：

- **RAG 本身的"智力"问题** — 切多大、用什么 embedding、要不要 reranker、混合检索权重 —— 全靠你自己。
- **评测与质量** — `RetrievalQA` 这种一行魔法链，效果几乎一定输给认真拼装的自定义 pipeline。
- **抽象税** — 栈深、import 路径乱、版本断代严重；只调一个 Provider 几个 endpoint 时裸 SDK 比 LangChain 更简洁。

#### 什么时候用 / 不用

| 场景 | 该用 | 别用 |
| --- | --- | --- |
| Provider 数量 | 跨 ≥ 2 个 Provider | 只用一家 |
| 集成范围 | 用 ≥ 5 个 Loader / 数据源 | 自己一个 PDF parser 就够 |
| 工作流复杂度 | Agent / 多步链 / 人机协作 | 单次问答、纯生成 |
| 可观测性 | 已经用 LangSmith | 不在乎 trace |
| 性能 | 普通业务 | 性能敏感（抽象层有开销） |

#### 一句话总结

**LangChain 给你砖，但不给你房子** —— 它的价值在协作层（工程化、标准化、生态）而非算法层（让 RAG 更准）。这个区分搞清楚了使用姿势就对了：拿它当 stdlib 用，别拿它当智能黑箱。

### 1.7 RAGAS

RAGAS 是一个基于 RAG 的评测框架，核心思想是用 LLM 来评测 RAG 的效果，属于 LLM as Judge 的范畴。学习如何接入并测试 Naive RAG 的检索质量可以帮助我们有效改善 RAG 系统的性能。

### 1.8 Naive RAG 总结

Naive RAG 作为 LLM 应用爆发初期的技术目前很难再适应生产级的需求，但是依然有宝贵的学习价值，也是做产品原型的时候最常用的简单 RAG 方案。

#### 六大核心问题

| 问题 | 描述 | 表现 |
| --- | --- | --- |
| 检索质量差 | 简单的向量相似度可能检索到不相关内容 | 答非所问 |
| 分块不合理 | 固定大小分块可能切断语义 | 上下文不完整 |
| 缺乏查询理解 | 用户原始口语化查询直接拿去检索，没有改写 / 扩展 | 检索召回率低 |
| 无重排序 | 直接使用原始查询检索 Top-K，可能包含噪声 | 相关内容排名靠后 |
| 上下文利用差 | 简单拼接检索结果直接喂给 LLM | "Lost in the Middle" 问题 |
| 无法处理复杂问题 | 单次检索无法处理多跳推理 | 复杂问题答错 |

## 二、Advanced RAG

### 2.1 从 Naive RAG 到 Advanced RAG

| Naive RAG 问题      | 具体表现                  | Advanced RAG 解决方案         |
| ------------------- | ------------------------- | ----------------------------- |
| 检索质量差          | 向量相似度 ≠ 语义相关性   | 混合检索、重排序              |
| 分块语义不完整      | 固定分块切断上下文        | 句子窗口、父文档检索          |
| 缺乏查询理解        | 用户原始查询不适合检索    | 查询改写、Multi-Query、HyDE   |
| Top-K 有噪声        | 相关内容排名靠后          | Cross-Encoder 重排序          |
| Lost in the Middle  | LLM 忽略中间内容          | Long Context Reorder          |
| 无法处理复杂问题    | 单次检索无法多跳推理      | Self-RAG、Adaptive-RAG        |

### 2.2 预检索优化：上下文增强分块策略

chunk 的大或者小有很多问题，小块的检索精度比大块高，但是大块比小块的上下文会更加完整，如果是 Naive RAG 其实无论如何平衡都需要做取舍。精度和完整性只能二选一。

Advanced RAG 通过上下文增强分块策略，结合**句子窗口**和**父文档检索**两种主要模式，既保证了检索的精度，又保留了上下文的完整性。简单来说就是小块检索、大块回答。（语义分块另算）

两种方式底层哲学一致，核心区别在于句子窗口以句子做索引、父文档以文档块做索引。句子窗口返回前后 N 个句子上下文偏动态，父文档检索返回整个父块上下文固定。句子窗口自定义而父文档检索 LangChain 内嵌支持了。

- 句子窗口检索适用场景：问答、客服对话、长文档分析、代码检索
- 父文档检索适用场景：论文检索、新闻检索、百科检索、法律文档检索

父文档的参数调优：

| 参数       | 推荐值        | 说明                                   |
| ---------- | ------------- | -------------------------------------- |
| 父块大小   | 800-1500 字符 | 提供足够上下文，但别超过 LLM 窗口限制  |
| 子块大小   | 150-300 字符  | 足够精确匹配，保持语义完整             |
| 父块重叠   | 100-200 字符  | 保持章节连贯性                         |
| 子块重叠   | 20-50 字符    | 避免关键词被切断                       |

#### 语义分块

核心是通过给文档每一个句子一个 embedding 并计算相邻句子的语义相似度，在相似度分数骤降的地方进行分块。语义分块的好处是可以保证每个块的语义完整性，缺点是分块大小不固定，可能会过大或者过小，核心就在于句子窗口的选取以及断点阈值的确定，具体参考以下的两张表：

**1. 核心参数**

| 参数名                       | 类型              | 核心作用                                                       | 示例值 / 常用值                                          | 补充说明                                                                                                                              |
| ---------------------------- | ----------------- | -------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `breakpoint_threshold_type`  | 字符串            | 定义"语义断点"的判定阈值类型，即如何界定"相似度足够低的分割点" | `"percentile"` / `"standard_deviation"` / `"interquartile"` | 常用值：`percentile`（百分位，如 90 表示取前 90% 相似度的临界值）；`standard_deviation`（标准差）；`interquartile`（四分位数）         |
| `breakpoint_threshold_amount`| 数值（int/float） | 配合阈值类型的具体数值，设定语义分割的临界值                   | `90`（percentile 类型）、`1.5`（standard_deviation 类型） | 以 `percentile=90` 为例：仅当两段文本的语义相似度低于 90 百分位的临界值时，才判定为"断点"进行分块                                     |
| `buffer_size`                | 整数              | 语义计算的滑动窗口大小，控制相邻文本片段的上下文窗口范围       | `1` / `2` / `3`                                          | 窗口越大，单次比较纳入的上下文越多，分块越平滑                                                                                        |

**2. 断点阈值类型的选取**

| 阈值类型             | 原理                       | 适用场景                 |
| -------------------- | -------------------------- | ------------------------ |
| `percentile`         | 基于相似度分布的百分位数   | 通用场景（推荐默认）     |
| `standard_deviation` | 基于标准差检测异常值       | 相似度分布较稳定的文档   |
| `interquartile`      | 基于四分位距检测离群点     | 对异常值敏感的场景       |
| `gradient`           | 基于相似度变化梯度         | 语义边界明显的文档       |

### 2.3 预检索优化：查询理解和改写

查询理解和改写的核心是将用户原始查询转化为更适合检索的形式，提升检索的相关性和准确性。常见的方法包括：

- 查询改写（Query Rewriting）：将用户查询重新表述，使其更符合检索引擎的预期输入格式。
- 多查询生成（Multi-Query Generation）：从原始查询生成多个相关查询，增加检索覆盖面。
- HyDE（Hypothetical Document Embeddings）：生成假设性文档来增强查询的语义表达。
- 查询分解（Query Decomposition）：将复杂查询分解为多个简单子查询，逐步检索和推理。

#### 查询改写

局限在于，可能改错问题意图 + 增加延迟 + 需要额外的 LLM 调用 + 改写的质量取决于改写的 Prompt 的设计。

#### 多查询

多查询生成的核心是从用户的原始查询出发，生成多个相关的查询变体，以增加检索的覆盖面和相关性。这种方法可以帮助捕捉用户查询中可能存在的不同表达方式或潜在意图，从而提高检索结果的质量，但是同样的，这方法只适用于开放性问题，封闭性问题（如事实查询）不适用。

#### HyDE

问答、技术文档检索、文档和表述差异大的时候适用，但是不适用于事实查询、新闻动态和简单关键词匹配的场景。

#### 查询分解

同查询改写，也很吃 prompt 质量和分解逻辑的设计。

### 2.4 检索优化：混合检索和多路召回

混合检索和多路召回的核心是结合不同类型的检索方法（如基于向量的语义检索和基于关键词的传统检索）来提高检索结果的相关性和覆盖面。通过融合多种检索策略，可以更全面地捕捉用户查询的意图和文档的相关性，从而提升整体检索性能。总结一句话：**关键词匹配 + 词频统计**（Sparse/BM25）。

#### BM25

BM25 是一种基于词频和逆文档频率的检索算法，适用于需要精确匹配关键词的场景，如事实查询、新闻动态和简单关键词匹配的场景。BM25 通过计算文档中关键词的出现频率以及关键词在整个文档集合中的稀有程度来评估文档与查询的相关性，适合处理结构化文本和短文本查询。

```bash
BM25 score = IDF(q) * ((f(q, D) * (k1 + 1)) / (f(q, D) + k1 * (1 - b + b * (|D| / avgDL))))
# 简化含义： 词重要性 * 词频贡献(TF) * 文档长度惩罚
```

其中：

- `IDF(q)`：逆文档频率，衡量关键词在整个文档集合中的稀有程度。
- `f(q, D)`：关键词在当前文档 D 中的出现频率。
- `|D|`：文档 D 的长度。
- `avgDL`：文档集合的平均长度。
- `k1` 和 `b`：调节参数，控制词频贡献和文档长度惩罚的权重。

#### 混合检索

混合检索通过结合 BM25 和向量检索的结果，可以同时利用关键词匹配的精确性和语义检索的相关性，从而提高整体检索性能。常见的混合策略包括：

- **线性融合**：将 BM25 和向量检索的得分进行加权平均，得到最终的相关性评分。
- **级联检索**：先使用 BM25 进行初步筛选，然后对筛选结果进行向量检索的精细排序。
- **交叉验证**：对 BM25 和向量检索的结果进行交叉验证，保留两者都认为相关的文档。

混合检索在选择检索器权重的时候参考经验值：

| 场景                   | BM25 权重 | 向量权重 | 原因                       |
| ---------------------- | --------- | -------- | -------------------------- |
| 技术文档（代码、API）  | 0.5       | 0.5      | 专有名词多，需要精确匹配   |
| 客服问答（口语化）     | 0.3       | 0.7      | 语义理解更重要             |
| 法律 / 医学（专业术语）| 0.6       | 0.4      | 术语精确匹配很重要         |
| 通用场景               | 0.4       | 0.6      | 默认推荐值                 |

专有名词更多的场景 BM25+0.1，口语化的场景 BM25-0.1。

#### RRF（倒数排名）融合算法

```bash
RRF score = sum(1 / (k + rank_i))
# 其中 k 是一个常数（通常取 60），rank_i 是文档在各个检索器中的排名
```

RRF（Reciprocal Rank Fusion）是一种基于排名的融合算法，通过对多个检索器的排名进行加权平均来计算最终的相关性评分。RRF 的核心思想是给予排名靠前的文档更高的权重，从而提升整体检索性能。RRF 在处理多个检索器结果时具有较好的鲁棒性，能够有效地融合不同类型的检索结果。

#### 多路召回

多路召回通过同时使用多个检索器（如 BM25、向量检索、语义分块等）来增加检索的覆盖面和相关性。每个检索器负责捕捉不同类型的相关文档，从而提高整体检索性能。多路召回适用于需要综合考虑多个维度的场景，如技术文档检索、复杂问答等。

**多检索方法 + 多数据源**是核心，比如技术文档检索可以同时检索代码库、API 文档和社区问答等多个数据源，增加检索的覆盖面和相关性，最后融合的部分可以使用 RRF 或者加权平均等方法。

多路召回的原则应该符合：

- 互补性：不同检索器应该能够捕捉到不同类型的相关文档，避免过度重叠。
- 权重平衡：重要的路径返回的结果更多。
- 去重处理：对于多个检索器返回的结果进行去重，避免重复文档影响最终结果的质量。
- 性能优化：合理设置每个检索器的返回数量，避免过多无关文档影响性能和结果质量，路径也不要太多。

典型的场景：多个独立知识库 + 复杂业务系统（需要整合多种信息源和信息类型的种类）。

### 2.5 后检索优化：重排序 Reranking

重排序（Reranking）是指在初步检索结果的基础上，使用更复杂的模型（如 Cross-Encoder）对检索结果进行重新评估和排序，以提升最终返回结果的相关性和准确性。重排序通常在初步检索阶段之后进行，利用更丰富的上下文信息和更强大的模型能力来优化检索结果的质量。

## 三、GraphRAG

GraphRAG 是 Microsoft Research 开源的知识图谱增强 RAG 框架，使用 CLI 而非 Python 代码驱动，关键在于 `settings.yaml` 配置 + 输入数据 + 索引/查询命令。

### 3.1 工作流

```bash
# 1. 安装
uv pip install graphrag

# 2. 初始化项目（生成 settings.yaml + prompts/）
graphrag init --root .

# 3. 把语料放到 input/ 下

# 4. 构建索引（最耗时，涉及实体抽取、关系抽取、社区检测、社区报告生成）
graphrag index --root .

# 5. 查询
graphrag query --root . --method local  "X 创立了哪些公司？"
graphrag query --root . --method global "这些公司主要竞争领域有哪些？"
graphrag query --root . --method drift  "分析他们的共同特点"
```

### 3.2 三种 search 方式

- **Local Search**：针对特定实体的问题，使用图的局部邻域。适合事实型、定向型问题。
- **Global Search**：全局概览类问题，使用社区报告（已经被 LLM 压缩过的二次摘要）。适合归纳、对比类问题。
- **DRIFT Search**：深入探索类问题，从一个实体出发动态扩展邻域。适合"挖掘相关线索"型问题。

### 3.3 与传统 RAG 的本质差异

向量 RAG 看到的永远是 top-k 片段（局部视角），GraphRAG 在索引阶段就把整篇语料压成了"实体—关系—社区"的结构化形式，因此对全局性、对比性问题更有优势；但代价是索引阶段需要大量 LLM 调用，耗时长、成本高、对中文场景还需要做 prompt 本地化。

### 3.4 故障排查

如果 `graphrag index` 卡在 `create_community_reports` 或部分 parquet 文件缺失：

```bash
rm -rf output cache
graphrag index --root . --verbose
grep -iE "community_reports|create_community_reports|error|exception" logs/*
```
