# Advanced RAG

## 从Naive RAG到Advanced RAG

| Naive RAG 问题      | 具体表现                  | Advanced RAG 解决方案         |
| ------------------- | ------------------------- | ----------------------------- |
| 检索质量差          | 向量相似度 ≠ 语义相关性   | 混合检索、重排序              |
| 分块语义不完整      | 固定分块切断上下文        | 句子窗口、父文档检索          |
| 缺乏查询理解        | 用户原始查询不适合检索    | 查询改写、Multi-Query、HyDE   |
| Top-K 有噪声        | 相关内容排名靠后          | Cross-Encoder 重排序          |
| Lost in the Middle  | LLM 忽略中间内容          | Long Context Reorder          |
| 无法处理复杂问题    | 单次检索无法多跳推理      | Self-RAG、Adaptive-RAG        |

## 预检索优化：上下文增强分块策略

chunk的大或者小有很多问题，小块的检索精度比大块高，但是大块比小块的上下文会更加完整，如果是Naive RAG其实无论如何平衡都需要做取舍。精度和完整性只能二选一。

Advanced RAG 通过上下文增强分块策略，结合**句子窗口**和**父文档检索**两种主要模式，既保证了检索的精度，又保留了上下文的完整性。简单来说就是小块检索、大块回答。(语义分块另算)

两种方式底层哲学一致，核心区别在于句子窗口以句子做索引、父文档以文档块做索引。句子窗口返回前后N个句子上下文偏动态，父文档检索返回整个父块上下文固定。句子窗口自定义而父文档检索LangChain内嵌支持了。

- 句子窗口检索适用场景： 问答、客服对话、长文档分析、代码检索
- 父文档检索适用场景： 论文检索、新闻检索、百科检索、法律文档检索

父文档的参数调优：

| 参数       | 推荐值        | 说明                                   |
| ---------- | ------------- | -------------------------------------- |
| 父块大小   | 800-1500 字符 | 提供足够上下文，但别超过 LLM 窗口限制  |
| 子块大小   | 150-300 字符  | 足够精确匹配，保持语义完整             |
| 父块重叠   | 100-200 字符  | 保持章节连贯性                         |
| 子块重叠   | 20-50 字符    | 避免关键词被切断                       |

- 语义分块
核心是通过给文档每一个句子一个embedding并计算相邻句子的语义相似度，在相似度分数骤降的地方进行分块。语义分块的好处是可以保证每个块的语义完整性，缺点是分块大小不固定，可能会过大或者过小，核心就在于句子窗口的选取以及断点阈值的确定，具体参考以下的两张表：

**1. 核心参数**

| 参数名                       | 类型              | 核心作用                                                       | 示例值 / 常用值                                          | 补充说明                                                                                                                              |
| ---------------------------- | ----------------- | -------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `breakpoint_threshold_type`  | 字符串            | 定义"语义断点"的判定阈值类型，即如何界定"相似度足够低的分割点" | `"percentile"` / `"standard_deviation"` / `"interquartile"` | 常用值：`percentile`（百分位，如 90 表示取前 90% 相似度的临界值）；`standard_deviation`（标准差）；`interquartile`（四分位数）         |
| `breakpoint_threshold_amount`| 数值（int/float） | 配合阈值类型的具体数值，设定语义分割的临界值                   | `90`（percentile 类型）、`1.5`（standard_deviation 类型） | 以 `percentile=90` 为例：仅当两段文本的语义相似度低于 90 百分位的临界值时，才判定为"断点"进行分块                                     |
| `buffer_size`                | 整数              | 语义计算的滑动窗口大小，控制相邻文本片段的上下文窗口范围       | `1` / `2` / `3`                                          | 窗口越大，单次比较纳入的上下文越多，分块越平滑                                                                                        |

**2. 断点阈值类型的选取**

| 阈值类型             | 原理                       | 适用场景                 |
| -------------------- | -------------------------- | ------------------------ |
| `percentile`         | 基于相似度分布的百分位数   | 通用场景（推荐默认）     |
| `standard_deviation` | 基于标准差检测异常值       | 相似度分布较稳定的文档   |
| `interquartile`      | 基于四分位距检测离群点     | 对异常值敏感的场景       |
| `gradient`           | 基于相似度变化梯度         | 语义边界明显的文档       |

## 预检索优化：查询理解和改写

查询理解和改写的核心是将用户原始查询转化为更适合检索的形式，提升检索的相关性和准确性。常见的方法包括：

- 查询改写（Query Rewriting）：将用户查询重新表述，使其更符合检索引擎的预期输入格式。
- 多查询生成（Multi-Query Generation）：从原始查询生成多个相关查询，增加检索覆盖面。
- HyDE（Hypothetical Document Embeddings）：生成假设性文档来增强查询的语义表达。
- 查询分解（Query Decomposition）：将复杂查询分解为多个简单子查询，逐步检索和推理。

### 查询改写

局限在于，可能改错问题意图+增加延迟+需要额外的LLM调用+改写的质量取决于改写的Prompt的设计。

### 多查询

多查询生成的核心是从用户的原始查询出发，生成多个相关的查询变体，以增加检索的覆盖面和相关性。这种方法可以帮助捕捉用户查询中可能存在的不同表达方式或潜在意图，从而提高检索结果的质量，但是同样的，这方法只适用于开放性问题，封闭性问题（如事实查询）不适用。

### HyDE

问答、技术文档检索、文档和表述差异大的时候适用，但是不适用于事实查询、新闻动态和简单关键词匹配的场景。

### 查询分解

同查询改写，也很吃prompt质量和分解逻辑的设计。

## 检索优化：混合检索和多路召回

混合检索和多路召回的核心是结合不同类型的检索方法（如基于向量的语义检索和基于关键词的传统检索）来提高检索结果的相关性和覆盖面。通过融合多种检索策略，可以更全面地捕捉用户查询的意图和文档的相关性，从而提升整体检索性能。总结一句话：**关键词匹配+词频统计**(Sparse/BM25)。

### BM25

BM25 是一种基于词频和逆文档频率的检索算法，适用于需要精确匹配关键词的场景，如事实查询、新闻动态和简单关键词匹配的场景。BM25 通过计算文档中关键词的出现频率以及关键词在整个文档集合中的稀有程度来评估文档与查询的相关性，适合处理结构化文本和短文本查询。

```bash
BM25 score = IDF(q) * ((f(q, D) * (k1 + 1)) / (f(q, D) + k1 * (1 - b + b * (|D| / avgDL))))
# 简化含义： 词重要性 * 词频贡献(TF) * 文档长度惩罚
```

其中：

- `IDF(q)`：逆文档频率，衡量关键词在整个文档集合中的稀有程度。
- `f(q, D)`：关键词在当前文档 D 中的出现频率。
- `|D|`：文档 D 的长度。
- `avgDL`：文档集合的平均长度。
- `k1` 和 `b`：调节参数，控制词频贡献和文档长度惩罚的权重。
