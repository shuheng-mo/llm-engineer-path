# Advanced RAG Q&A

1. 对于语义分块有的块大、有的块小的问题，有没有可能在特殊场景下导致语义检索的不稳定？正如大块和小块的那种矛盾，语义分块有没有可能分出来检索效果还不如Naive RAG的块？这种情况下我们是考虑句子窗口分块还是退回到Naive RAG？
2. 混合检索除了加权平均之外是不是还有别的策略？级联检索和交叉验证这些在哪些场景下适用？有没有一些实际的例子可以说明这些策略的优缺点和适用场景？
3. RRF实际上可不可以理解为就是一种简单的加权平均？它和其他加权平均方法相比有什么独特的优势或者局限性？在实际应用中我们应该如何选择使用RRF还是其他加权平均方法？
4. Cross-Encoder（比如 bge-reranker-v2-m3）和向量检索的根本差别在于：前者把 query 和 doc 拼在一起进同一次 attention，后者各自独立向量化。这种"晚交互"为什么效果更好？既然 Cross-Encoder 这么强，为什么不能直接用它检索全库、跳过向量检索这一步？两者结合的本质是不是就是召回靠快、排序靠准的算力权衡？
5. 让 LLM 直接给 (问题, 文档) 打 0-10 分这种做法，结果到底稳不稳？同一个文档调用两次可能分数都不一样，不同文档之间的分数也不一定可比（毕竟 LLM 没看到其他候选）。要不要改成一次喂多个文档让它直接排序？这两种打分方式在准确率和成本上各有什么取舍？
6. Long Context Reorder 的"奇数前、偶数倒序"是基于 Lost in the Middle 的经验法则，但这个现象在不同 LLM 上的强度并不一致（GPT-4、Claude、Qwen 都有差异）。这种重排是不是应该针对具体模型做实验验证？如果模型本身已经做了长上下文优化，强行 reorder 会不会反而引入噪声？
7. 上下文压缩让 LLM 从每个文档里抽相关句子，本质上是用一次额外的 LLM 调用换 token 节省，但同时也把"抽错"这个新风险引入了进来。在什么场景下压缩带来的收益（省 token、减少干扰）大于风险（漏掉关键信息、抽取幻觉）？有没有什么办法能评估压缩到底丢了多少东西？
8. Self-RAG 设计了四个反思点，每个都是一次 LLM 调用，最坏情况下回答一个问题要调用五六次模型。这种延迟和成本在生产环境真的扛得住吗？反思链条上某一步判断错了会不会一路错下去？能不能像原论文那样把反思能力蒸馏到一个小模型里？
9. Adaptive-RAG 的 A/B/C 三档分类完全依赖 LLM 自己判断问题复杂度，但 LLM 很容易把"看着简单的难题"误判成 A 类直接答，或者把"看着复杂的简单题"误判成 C 类去多步检索。这个分类器自己的准确率怎么评估？要不要干脆换成一个微调过的小模型来做路由或者有没有更好的办法？
10. 带引用的生成靠 LLM 自己在回答里标注 `[文档X]`，但模型经常乱标、漏标，甚至引用了根本没用到的文档。这种"引用幻觉"该怎么评估和缓解？除了在 prompt 里约束之外，有没有结构化输出或者事后用归因模型校验的做法？像 Perplexity 这类产品的引用机制大致是怎么做的？
